# DWarrenGroup — Entity Relationship Diagram

An interactive ERD for a star-schema analytics database behind an online
free-to-play game. Built for IFT 530: Advanced Database Management Systems
at Arizona State University.

**[View the diagram →](https://dw425.github.io/dwarrengroup-erd/)**

## What it shows

10 tables — 6 dimensions, 3 fact tables, 1 audit table — joined by 15 foreign
keys, with no circular references. Every dimension holds 10 rows and every
fact table 20–50, which is what the assignment asks a submitted script to
carry; the schema itself is designed for 100,000 users.

| | |
|---|---|
| **Dimensions** | `DimGeography`, `DimUser`, `DimAccount`, `DimPlan`, `DimProduct`, `DimCampaign` |
| **Facts** | `FactUserEvent` (one player action, 48 rows), `FactPayment` (one transaction, 30 rows), `FactSubscription` (one lifecycle change, 23 rows) |
| **Audit** | `DimPlanAudit`, written only by a trigger |

`DimGeography` is a role-playing dimension referenced five times — a user's
registered location and last-seen location, an account's billing location, and
the origin of every event and every payment. Comparing any two of those is what
makes impossible-travel fraud detection possible.

`SessionID` on `FactUserEvent` is a degenerate dimension: it groups events into
one sitting and needs no table of its own.

## Using it

Hover any table to isolate its relationships — 15 foreign keys crossing one
canvas is unreadable otherwise. Hovering a row in the foreign-key list does the
same thing. Line colour follows the parent table.

The page is a single self-contained file. No build step, no dependencies, no
network calls — the CSS, the SVG and the script are all inline.

## Source

The geometry is computed, not hand-drawn: box heights follow column counts and
every connector is routed from the real key positions. Generated by
`tools/erd_html.py` in the course repository, mirroring the column definitions
in `parts/30_tables.sql`.
